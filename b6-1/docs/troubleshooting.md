## 사례 1. SSH 접속 시 Permission denied (publickey)

### 증상

키 페어 파일을 지정해 SSH 접속을 시도했으나 인증 단계에서 거부되었다.

```
Warning: Permanently added '15.165.74.3' (ED25519) to the list of known hosts.
ec2-emfrntkf@15.165.74.3: Permission denied (publickey,gssapi-keyex,gssapi-with-mic).
```

### 가설

`Permission denied (publickey)`는 네트워크 도달에는 성공했으나 공개키 인증에서 실패했음을 의미한다. 가능한 원인을 세 가지로 나누었다.

- **가설 A**: `.pem` 파일 권한이 과도하게 열려 있어 SSH 클라이언트가 키 사용을 거부
- **가설 B**: 인스턴스에 등록된 키 페어와 다른 키를 사용
- **가설 C**: 로그인 사용자명이 잘못됨

### 검증

먼저 보안 그룹이나 라우팅 문제가 아님을 확정했다. 로그에 호스트 키 지문 교환이 성공하고 `known_hosts`에 등록되었다는 메시지가 남아 있는데, 이는 TCP 22번 연결이 수립되어 SSH 프로토콜 협상까지 진행되었다는 뜻이다. 네트워크 경로와 Security Group 인바운드 규칙은 정상이다.

이어서 에러 메시지 자체를 확인했다. 접속 시도한 사용자명이 `ec2-emfrntkf`로 기록되어 있었다. Amazon Linux 2023의 기본 사용자명은 `ec2-user`이며, `emfrntkf`는 한글 입력 상태에서 `user`를 입력했을 때 생성되는 문자열이다. **가설 C가 유력**하다고 판단했다.

### 조치

한/영 입력 상태를 전환한 뒤 올바른 사용자명으로 재시도했다.

```bash
ssh -i cody-aws-key.pem ec2-user@15.165.74.3
```

### 결과

접속에 성공했다. 가설 A, B는 검증할 필요 없이 배제되었다.

### 재발방지

접속 명령을 매번 직접 입력하지 않도록 `~/.ssh/config`에 호스트를 등록한다.

```
Host cody-server
    HostName 15.165.74.3
    User ec2-user
    IdentityFile ~/.ssh/cody-aws-key.pem
```

이후 `ssh cody-server`만으로 접속할 수 있어 사용자명 오타 가능성이 제거된다.

### 배운 점

`Permission denied (publickey)`는 원인이 세 가지뿐이며, 그중 무엇인지는 **에러 메시지에 이미 사용자명이 찍혀 있다**. 키 권한부터 확인하는 대신 에러 메시지 자체를 먼저 읽었다면 더 빨리 해결했을 것이다. 또한 이 에러가 났다는 사실 자체가 네트워크 계층은 정상이라는 정보를 담고 있어, 확인 범위를 애플리케이션 계층으로 좁힐 수 있다.

## 사례 2. IAM 사용자로 로그인 후 EC2 인스턴스가 조회되지 않음

### 증상

최소권한 검증을 위해 IAM 사용자 `cody-iam`으로 콘솔에 로그인했으나, EC2 인스턴스 목록이 비어 있었다. 권한 부족을 알리는 오류 배너는 표시되지 않았다.

### 가설

- **가설 A**: `AmazonEC2FullAccess` 정책이 사용자에게 제대로 연결되지 않음
- **가설 B**: 콘솔 리전이 인스턴스가 위치한 리전과 다름
- **가설 C**: 브라우저 세션이 IAM 사용자가 아닌 기존 계정으로 유지됨

### 검증

핵심 단서는 **오류 배너 없이 목록만 비어 있다**는 점이었다. 권한이 없어 목록을 조회하지 못하는 경우 콘솔은 명시적으로 접근 거부 메시지를 표시한다. 오류가 없다는 것은 API 호출 자체는 성공했고 결과가 0건이라는 뜻이므로, 가설 A는 가능성이 낮다.

EC2 리소스는 리전에 종속된다. 새 로그인 세션은 기본 리전(us-east-1)으로 시작되는데, 인스턴스는 ap-northeast-2에 생성했다. **가설 B**를 우선 검증했다.

### 조치

콘솔 우측 상단 리전 선택기를 **아시아 태평양(서울) ap-northeast-2**로 변경했다.

### 결과

인스턴스 `cody-server`가 정상적으로 조회되었다. 동시에 우측 상단에 `cody-iam` 사용자명이 표시되어 가설 C도 배제되었다(시크릿 창으로 접속했기 때문에 기존 세션이 유입되지 않았다).

### 재발방지

- IAM 사용자 로그인 후 작업 시작 전에 리전을 먼저 확인하는 것을 습관화한다.
- 계정 전환 검증은 반드시 시크릿 창에서 수행한다. 기존 창에서는 원래 계정 세션이 유지되어 IAM 사용자로 테스트한다고 생각하면서 실제로는 관리자 권한으로 조회하게 될 수 있고, 이 경우 최소권한 검증 자체가 무의미해진다.
- 자격 증명이 헷갈릴 때는 CloudShell에서 `aws sts get-caller-identity`로 현재 주체를 확인한다.

### 배운 점

**"리소스가 안 보인다"는 증상은 원인이 두 가지로 갈리며, 오류 배너의 유무로 구분된다.** 배너 없이 목록만 비어 있으면 리전 또는 필터 문제이고, 접근 거부 배너가 뜨면 권한 문제다. 이 구분 기준을 알면 확인 순서를 잘못 잡아 시간을 낭비하지 않는다.

## 사례 3. SSH 인바운드 규칙이 전체 개방(0.0.0.0/0)으로 설정됨

### 증상

에러가 발생하지 않은 사례다. 외부 접속 검증을 마친 뒤 보안 그룹 인바운드 규칙을 최종 확인하는 과정에서, SSH 규칙의 소스가 개인 IP가 아닌 `0.0.0.0/0`으로 설정되어 있음을 발견했다.

```
SSH   TCP   22   0.0.0.0/0
HTTP  TCP   80   0.0.0.0/0
```

기능은 정상 동작했기 때문에 증상으로 드러나지 않았고, 규칙을 직접 열람하지 않았다면 그대로 제출되었을 상태였다.

### 가설

- **가설 A**: 인스턴스 생성 마법사에서 SSH 소스 기본값이 `0.0.0.0/0`(Anywhere)으로 제공되며, 이를 `내 IP`로 변경하지 않은 채 생성함
- **가설 B**: 생성 후 접속 문제를 해결하는 과정에서 임시로 넓게 열어둔 뒤 되돌리지 않음

### 검증

두 규칙 모두 소스가 동일하게 `0.0.0.0/0`이고 별도 수정 이력이 없다는 점에서, 생성 시점의 기본값이 그대로 유지된 것으로 판단했다. AWS 콘솔의 인스턴스 시작 마법사는 SSH 규칙을 기본으로 추가하면서 소스를 Anywhere로 제시하고, 화면에 경고 문구를 함께 표시한다. **가설 A**가 원인이다.

### 조치

보안 그룹 → 인바운드 규칙 편집 → SSH 규칙의 소스를 **내 IP**로 변경 후 저장했다.

```
SSH   TCP   22   121.135.181.35/32
HTTP  TCP   80   0.0.0.0/0
```

기존에 수립된 SSH 세션은 연결 추적(connection tracking)에 의해 유지되므로 작업 중 접속이 끊기지 않았다.

### 결과

SSH는 관리자 개인 IP에서만, HTTP는 전체에서 접근 가능한 상태가 되었다. 최소 권한 원칙에 부합하며 과제 요구사항을 충족한다. 증빙은 `docs/images/06-security-group.png`에 보관했다.

### 재발방지

- 인스턴스 생성 마법사의 네트워크 설정에서 SSH 소스를 반드시 `내 IP`로 지정한다. 기본값을 신뢰하지 않는다.
- 구축 완료 후 **보안 그룹 인바운드 규칙 전수 확인**을 체크리스트 항목으로 고정한다. 기능 검증(접속되는가)과 보안 검증(과도하게 열려 있지 않은가)은 별개의 절차다.
- 가정용 인터넷은 공인 IP가 변동될 수 있다. SSH 접속이 갑자기 실패하면 이 규칙의 IP 갱신을 먼저 확인한다. 다인 협업 환경이라면 개별 IP 대신 지정된 대역이나 SSM Session Manager 사용을 검토한다.

### 배운 점

**정상 동작하는 시스템도 잘못 구성되어 있을 수 있다.** 앞의 두 사례는 에러가 문제를 알려준 경우지만, 이 건은 아무 증상이 없었다. 보안 설정의 결함은 대체로 이런 형태로 나타난다 — 지나치게 열린 규칙은 기능을 방해하지 않으므로 사용자가 인지할 계기가 없고, 실제 침해가 발생한 뒤에야 드러난다.

따라서 보안 항목은 증상 기반으로 발견할 수 없으며, **주기적인 능동 점검이 유일한 탐지 수단**이다. 이것이 구성 검토와 감사(audit)가 별도 절차로 존재하는 이유다.

## 종합

사례 1과 2는 **에러 메시지에 원인을 특정할 단서가 이미 포함되어 있었다**. 사례 1은 잘못된 사용자명이, 사례 2는 오류 배너의 부재가, 사례 3은 거부된 액션의 네임스페이스가 각각 결정적 단서였다.

또한 사례 1과 2에서 확인했듯 **에러의 종류 자체가 어느 계층까지는 정상인지를 알려준다.** SSH 인증 실패는 네트워크 계층이 정상임을, 빈 목록은 권한이 정상임을 각각 내포한다. 증상을 정확히 읽으면 검증해야 할 가설의 수를 크게 줄일 수 있다.

반면 사례 3은 성격이 다르다. 아무 증상이 없었고, 시스템은 정상 동작했다. 보안 설정의 결함은 기능을 방해하지 않기 때문에 증상 기반 탐지가 통하지 않으며, 능동적인 구성 점검으로만 발견된다. **"동작한다"와 "올바르게 구성되었다"는 서로 다른 명제**라는 것이 이번 실습에서 얻은 가장 중요한 교훈이다.

| 사례 | 증상 유무 | 발견 경로 | 조치 |
| --- | --- | --- | --- |
| 1. SSH 인증 실패 | 있음 | 에러 메시지 | 사용자명 정정 |
| 2. 인스턴스 미조회 | 있음 (오류 배너 없음) | 증상의 형태 분석 | 리전 변경 |
| 3. SSH 전체 개방 | **없음** | 능동적 구성 점검 | 소스를 `/32`로 제한 |
